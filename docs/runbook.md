# Runbook: API повільний або відповідає 5xx

- **Алерт(и):** `ApiLatencyP95High` (`p95_ms > 2000` протягом 3 хв) і `Api5xxRateHigh` (`error_rate > 0.05` протягом 3 хв). Обидва — пейдж у `#poshtomat-oncall` і дзвінок черговому.
- **Що це означає для користувачів:** екран поштомата пише «Сервіс зайнятий, спробуйте пізніше», мешканці не можуть забрати посилку, а служба доставки — зареєструвати нову.
- **Скільки є часу:** запасу майже немає: у попередньому інциденті за 3 хвилини помилок стало 12 %. Мета — відновити сервіс за 15 хвилин, навіть якщо причина ще невідома.

> **Перед використанням — припущення:** тека репозиторію на VM — `poshtomat-repo`, дашборд моніторингу — `poshtomat-dashboard`, кожен реліз позначено git-тегом версії (`v1.7.3`, `v1.8.0`). У документації цього не вказано: перевірте й виправте, якщо інакше. Команди для VM не перевірялись на справжньому сервері.

## Перші 5 хвилин

Усі команди виконуйте на VM, попередньо зайшовши на неї й перейшовши в теку репо:

```bash
ssh poshtomat-prod-1
cd poshtomat-repo   # припущення, див. вище
```

1. **Напишіть у `#poshtomat-oncall`:** «Взяв(ла) пейдж, дивлюсь».
2. **Перевірте, чи не було нещодавно деплою.** Це найважливіше питання:

   ```bash
   docker compose -f deploy/compose.yaml ps --format 'table {{.Service}}\t{{.Status}}'
   git log -3 --format='%h %ci %s'
   ```

   `Up` менше ніж 30 хвилин або свіжий коміт → **одразу відкат**, розслідування потім (див. «Що робити»). Не чекайте, поки знайдете причину.
3. **Перевірте, чи справді зачеплена БД.** Запит із недійсним токеном безпечний, нічого не змінює, але бере з'єднання з пулу:

   ```bash
   curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' -H 'Authorization: Bearer probe' http://localhost:8080/admin/parcels
   ```

   `403` швидше ніж за 1 с — пул працює. `503` або час понад 2 с — пул вичерпано.

**`/health` не допоможе:** він не звертається до БД і відповідає `200` навіть під час такого збою.

## Діагностика

| Питання | Команда | Як читати результат |
|---|---|---|
| Які саме помилки? | `docker compose -f deploy/compose.yaml logs --since 15m --no-log-prefix api \| grep '"level":"error"' \| grep -o '"error":"[^"]*"' \| sort \| uniq -c \| sort -rn` | Багато `db pool wait timeout` → пул, крок «Як підтвердити причину». Поодинокі `reading 'trim'` → відомий фоновий дефект, близько 30 на годину, не причина |
| Яка версія працює? | `curl -s http://localhost:8080/health` | Поле `version`; порівняйте з попереднім випуском |
| Який пул передано API? | `docker compose -f deploy/compose.yaml exec -T api printenv \| grep '^DB_POOL'` | Очікується `DB_POOL_MAX=20` і `DB_POOL_WAIT_MS=2000`. Немає `DB_POOL_MAX` або є інша назва → пул непомітно став 4 |
| Скільки запитів до API за останню хвилину впали через пул? | `docker compose -f deploy/compose.yaml logs --since 1m --no-log-prefix api \| grep -c 'db pool wait timeout'` | `0` — пул не проблема. Десятки чи сотні — проблема триває |
| Скільки з'єднань із базою? | `sudo -u postgres psql -d poshtomat -c "select count(*) from pg_stat_activity where datname='poshtomat'"` | Для орієнтиру: API і worker мають по 20 з'єднань максимум, а API зазвичай тримає 10–13. Набагато менше на піку підозріло, близько 40 → перевірте, чи не вичерпано ліміт самої БД |
| Чи не вікно бекапу? | `date; sudo tail -n 5 /var/log/poshtomat/backup.log` | З 02:00 до 02:30 за Києвом записи в БД чекають або падають; після 02:30 мало б минути само |
| Чи є пейдж про SMS? | `docker compose -f deploy/compose.yaml logs --since 5m --no-log-prefix worker \| grep -c 'rate limited'` | Десятки 429 за хвилину в години пік — **норма**. API не працює з SMS, тому це не пояснює 503 на екрані |

Метрики `db_pool_in_use`, `db_pool_waiting` і `p95_ms` дивіться в моніторингу: `poshtomat-dashboard` (припущення, див. вище). Звичайна картина в години пік: зайнято 10–13, очікувань 0, p95 близько 240 мс.

**Не вводьте себе в оману.** Усе це буває і в справний день: heap до 82 % і рядки `heap usage high`, поодинокі `TLS handshake timeout`, 429 від SMS-провайдера.

## Як підтвердити причину

Причина в пулі, якщо одночасно виконуються дві умови:

1. **`db_pool_in_use` рівно на одному значенні, а `db_pool_waiting` більше за 0**, хоча rps не вищий за звичайний.
2. **Практично всі 5xx мають текст `db pool wait timeout`** (перший рядок таблиці діагностики).

Щоб знайти причину зміни, порівняйте змінні з тим, що читає код:

```bash
grep -n 'env\.' app/src/config.js
docker compose -f deploy/compose.yaml config | grep -n 'DB_POOL'
```

Назва в compose має збігатися з `env.<НАЗВА>` у `app/src/config.js`. Якщо ні, код непомітно бере типове значення.

## Коли ескалювати і кого кликати

- **За 15 хв сервіс не відновлено, або потрібен відкат зі зміною схеми БД** → другий розробник у `#poshtomat-oncall`; він же на зв'язку поза чергуванням.
- **Є вплив на мешканців понад 15 хв** → координаторка проєкту: вона попереджає гарячу лінію.
- **Підозра на проблему SMS-провайдера** → `support@sms.example.net` і `status.sms.example.net`. Відповідають протягом робочого дня, тому не чекайте на них, перш ніж відкочуватись.
- **Номери телефонів чи коди могли потрапити не туди** → `dpo@example.org` протягом доби.
- **Загальна командна пошта** → `poshtomat-team@example.org`.

## Як переконатися, що все гаразд

Зачекайте 2–3 хвилини після дії, потім перевірте:

- **Пул працює:** команда з кроку 3 «Перших 5 хвилин» дає `403` швидше ніж за 1 с.
- **503 зникли:** `docker compose -f deploy/compose.yaml logs --since 2m --no-log-prefix api | grep -c '"status":503'` дає `0`.
- **Метрики:** p95 нижче 300 мс, `db_pool_waiting` дорівнює 0. Минулого разу p95 був 618 мс у першу хвилину, а 296 мс — у другу.
- **Пейджі:** `ApiLatencyP95High` і `Api5xxRateHigh` закрились, зазвичай протягом кількох хвилин.
- **Реальна видача:** гаряча лінія більше не отримує скарг із поштоматів.

Наприкінці напишіть у `#poshtomat-oncall`, що зроблено, і заведіть задачу на розбір.
